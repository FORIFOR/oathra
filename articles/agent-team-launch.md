3つの公開ページを比較するメモを、AIチームに作らせました。

調査役が初稿を書き、レビュー役が3件指摘し、調査役が修正する。ここまでは進みました。ところが、最終状態は **`partial`（一部完了）**。レビュー環境では出典ページを再取得できず、最後のレビューは予算上限にも達したためです。

「文章ができた」と「確かめ終わった」を分けて見たい。そのために作っているのが、ローカルで動く **Agent Team（リポジトリ名: Multibot）** です。MITで公開しています。

https://github.com/FORIFOR/Multibot

この記事では、実際の修正内容、かかった費用、未完了になった理由、手元での試し方を紹介します。Claude Codeを使っていて、成果物のレビューまで含めた自動化を試したい方向けです。

## 3つのページを比較させたら、何が直ったか

対象は、Deep Agents、DeerFlow、Agent Skillsの公開ページ。主張・対象読者・ライセンスを、出典付きで整理する調査でした。

レビューの指摘と、修正版での対応を要約するとこうなります。

| 指摘 | 修正版での対応 |
| --- | --- |
| DeerFlowの内部構成について、根拠引用のない記述がある | 該当する断定を削除し、未確認と明記 |
| Agent Skillsのページから公式リポジトリへのリンクを、確認できた範囲以上に断定している | リンクラベルの確認と、リンク先URLの未確認を分けて記載 |
| Deep Agentsの説明を「CLI」と言い換えている | 原文に近い「ターミナル上の既製コーディングエージェント」に修正 |

[初回レビュー](https://github.com/FORIFOR/Multibot/blob/main/docs/evidence/scenarios/research2/review.md.r1)と[修正後のレビュー](https://github.com/FORIFOR/Multibot/blob/main/docs/evidence/scenarios/research2/review-final.md.r1)を公開しています。

修正後のレビュー文書では、この3件の反映が `pass` になりました。ただし、**出典の原文照合は `unverified` のまま**です。さらに、出力の切り詰めでレビュー役が読めなかった範囲もあります。レビュー文書の一部が合格でも、実行全体の完了とは別に扱います。

## 手元で試す

`uv` と、ログイン済みのClaude Codeが必要です。次のコマンドで起動します。

```bash
uvx --from "git+https://github.com/FORIFOR/Multibot#subdirectory=backend" agentteam quickstart
```

最初に `claude -p` で小さな実通信を行い、ツール呼び出しと構造化出力を確認します。その後、`http://127.0.0.1:8787` でUIが開きます。フロントエンドはパッケージに同梱しています。

Claude Code経由ならAPIキーの入力は不要ですが、契約の利用枠を消費します。**OSSのライセンス料が無料であることと、モデル利用が無料であることは別です。** 起動時の疎通確認も実通信です。

最初の依頼には、自分が確認できる公開資料を使うと結果を判断しやすくなります。比較対象のURL、比較したい項目、取得できなかった場合の扱いを明示し、小さな成果物から試してください。

起動後は、成果物を開くだけでなく、レビュー対象の版と、最終報告の未検証項目も確認してみてください。

接続先はClaude API、OpenAI互換API、Ollamaも選べます。環境とモデルによって、計画の生成やレビューの完遂に差があります。[セットアップと確認済みの範囲](https://github.com/FORIFOR/Multibot#quickstart)をREADMEに載せています。

## レビューを「どのファイルの、どの版か」に結び付ける

仕組みは、次の順序です。

```text
依頼
 ↓
Master: 成果物・担当・依存関係を計画
 ↓
Runtime: 計画と権限・上限を検査
 ↓
Worker: 調査・制作 → 成果物を公開
 ↓
Reviewer: 特定の版を検証 → 指摘
 ↓
Worker: 修正 → 新しい版を公開
 ↓
Reviewer: 再検証
 ↓
Runtime: イベントから最終報告を組み立てる
```

成果物にはSHA-256のハッシュを付け、検証結果とレビューをその版に紐付けています。修正前の版に付いた合格を、修正後の版の検証として扱わないためです。

チャットには、ほかのBotの受信箱へ実際に配送した `message.sent` イベントを表示します。各Workerには、担当タスク・入力成果物への参照・自分宛ての受信箱を渡します。

イベントはSQLiteのWALモードで保存し、UIへSSEで配信します。最終報告は記録された検証結果から組み立てます。モデルが「終わった」と書いても、未実行の検証を合格にはしません。ただし、**検証自体の範囲や正しさには限界がある**ため、記録があるだけで成果物の正確性を保証するものでもありません。

### 停止条件もRuntimeに持たせる

ツール権限、書き込み範囲、予算、停止・再開をRuntimeで管理します。コマンドの実行にはDocker、またはmacOSのseatbeltサンドボックスを使います。どちらも利用できない場合は、明示的に隔離なしの実行を選ばない限り、コマンドを拒否します。

ローカルファーストですが、クラウドモデルへの接続時には、その接続先へ入力が送られます。隔離の範囲や注意点は[SECURITY.md](https://github.com/FORIFOR/Multibot/blob/main/SECURITY.md)に記載しています。

## 複数エージェントにすると、1体より良くなるのか

**今ある測定からは、品質が上がるとは言えません。**

50タスク×3回で比較を始めましたが、チーム側はClaude CLIの利用上限に達しました。2026年9月14日に既存記録を監査した結果です。

| 記録 | チーム | 単一エージェント |
| --- | ---: | ---: |
| 対象のタスク・反復ペア | 150 | 150 |
| 実行完了 | 47 | 150 |
| 一部完了 | 3 | 0 |
| プロバイダ上限による失敗 | 100 | 0 |

一部完了3件のうち2件も上限の影響を受けています。完了数と成果物の正解数は別です。単一側は、元の自動採点では146件正解、同義の日本語表現を受け入れる採点修正後には150件正解でした。元の判定も保存しています。

この評価は作成した評価入力を使っており、顧客業務150件の実績ではありません。また、プロバイダの利用可能条件が揃わず、チーム側の比較は完遂できていません。詳細と全件の集計元は[ベンチマーク監査記録](https://github.com/FORIFOR/Multibot/tree/main/docs/evidence/benchmark-2026-09-13)にあります。

ここから、上限・認証エラーが出たら待機中の評価を止め、記録を残して再開する処理も追加しました。失敗を取り除いて成功率を良く見せるより、同じ条件で続きを測れる状態にする必要がありました。

## どんな用途で試してほしいか

公開資料の比較メモ、コードと検証結果の引き渡し、文書の根拠確認など、**成果物と確認過程を一緒に受け取りたい作業**で試してもらいたいです。単発の短い質問なら、まず1体に頼む方が手軽です。

現状は、実行記録を公開して検証を進めている段階です。顧客データを使う有償PoCや本番導入には、組織ごとのデータ分離・認証・保存期間・運用監視などを別途詰める必要があります。

[ホームページ](https://forifor.github.io/Multibot/ja/#business)には業務利用の相談窓口を用意しています。まずは公開資料で、何を任せられ、どこに人の確認が残るかを確かめたいと考えています。

試して、レビューが見落とした点や止まった依頼があれば、機密情報を除いて[GitHub Issues](https://github.com/FORIFOR/Multibot/issues)に教えてください。今後の改善を追いたい方は、リポジトリにStarを付けてもらえると嬉しいです。
