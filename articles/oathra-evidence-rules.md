「たぶん大丈夫です」と「ご予約承りました」は、会話としてはどちらも前向きな返事です。しかし、プログラムから同じ「成功」として扱うと困ります。

電話AIのOSS [Oathra](https://github.com/FORIFOR/oathra) では、会話の生成と完了判定を分離し、**発言から抽出した条件への合意と、予約を確定した根拠を別々に管理する**ようにしました。

この記事では、曖昧な返事・代案・条件変更・取り消しをどう処理するか、実装を追って説明します。全文を理解するモデルではなく、正規表現と状態管理による判定です。

この設計は、電話相手の属性を推測してプロファイルを作るためのものではありません。判定対象は `CallContract` で宣言した項目に限定し、目的外の聞き取りや、同じ質問の繰り返しを避けます。追加の情報を扱うときは、目的・質問上限・同意・拒否時の停止を契約に含め、相手が明示した回答から業務用プロファイルを作れるよう発話の根拠を残します。

**対象読者**：音声AIやLLMエージェントの完了条件を、モデルの自己申告ではなくコードで検証したい開発者。

この記事を読み終えると、次の3点を自分の通話ログで確認できます。

- 相手の提案と、こちらが受けた条件を分けて記録する
- 「たぶん」「確認します」や聞き返しを確定にしない
- 確定後の価格変更・取り消しで、以前の完了を失効させる

## まず、判定が変わるところを見る

[ブラウザの証拠ラボ](https://forifor.github.io/oathra/?utm_source=zenn&utm_medium=article&utm_campaign=evidence_revision#sim)で「たぶん大丈夫」→「ご予約承りました」→「やはりお取りできませんでした」と押すと、未完了→完了→未完了と変わります。自由入力もできます。

https://x.com/forifori_dev/status/2099160731409379808

埋め込みが表示されない場合は、[サイトで30秒の動画を見る](https://forifor.github.io/oathra/#demo-video)こともできます。

本体と同じエンジンをブラウザで動かした実操作動画です。発言は操作例であり、実電話の録音ではありません。音声認識は介さず、文字を直接入力しています。

扱いたいのは、次のような違いです。

| 発言 | 必要な扱い |
| --- | --- |
| 「たぶん大丈夫ですが、まだ確定ではありません」 | 曖昧な返事で確定させない |
| 「19時は満席です。19時半なら空いています」 | 19時を候補から除き、19時半を提案として残す |
| 確定後に「料金は2万3500円になります」 | 以前の条件に対する確定を失効させる |
| 確定後に「やはりご予約をお取りできませんでした」 | 取り消し後の状態で再評価する |

## 最初に「値」と「確定」を分ける

エンジンへの入力は、話者・発言・時刻などを持つ `Utterance` です。処理は次の順で進みます。

1. `extractClaims` が発言から時刻・人数・価格などの候補を抽出する。
2. `EvidenceEngine.ingest` が相手側の応答と照合し、合意や訂正を記録する。
3. `engine.values()` が現在有効な確認済みの値を返す。
4. `evaluate` が必須項目・制約・接続状態を調べ、完了を判定する。

19時半が会話に登場しても、それだけでは確認済みの値になりません。店側の提案は発信側が受け、発信側の提案は店側が同意する必要があります。

予約の確定を表す `confirmed` はさらに別です。発信側が「予約できました」と言っても確認済みにはしません。これにより、AIの報告だけで完了する経路を切り離しています。

## 1. 否定と代案を、節ごとに分ける

「19時はいっぱいですが19時半なら空いております」を一文として抽出すると、19:00と19:30の両方が現れます。

そこで、句読点に加え、逆接の一部でも節を分けます。以下は[実装の抜粋](https://github.com/FORIFOR/oathra/blob/main/packages/evidence/src/extract.ts)です。

```ts
const sub = c.text.split(/(?<=ですが|ますが|けど|けれど|but\s)/);
```

各節に拒否表現があるかを調べ、抽出値に正負の属性を付けます。「19時はいっぱいですが」は否定、「19時半なら空いております」は肯定です。エンジンが提案として扱うのは肯定側の値なので、断られた19時を誤って提案にしません。

句読点で切る処理には落とし穴もあります。「21,100円」のカンマは文の区切りではありません。実装では桁区切りと小数点を先に保護してから節に分割しています。日本語の言い回しだけでなく、数値の正規化も判定の一部です。

## 2. 曖昧な返事と、聞き返しを同意にしない

曖昧語は `HEDGE_RE` で見ています。「たぶん」「と思います」「確認します」、英語の `probably` や `let me check` などです。

同意の判定は、単に「大丈夫です」に一致すればよいわけではありません。[`isAgreement`](https://github.com/FORIFOR/oathra/blob/main/packages/evidence/src/extract.ts) は次の条件を持ちます。

```ts
export function isAgreement(text: string, source: Speaker): boolean {
  return source === "callee"
    && AGREEMENT_RE.test(text)
    && !REFUSAL_RE.test(text)
    && !HEDGE_RE.test(text)
    && !QUESTION_RE.test(text.trim());
}
```

これにより「たぶん大丈夫です」を同意として扱わず、「その内容で合っておりますでしょうか？」のような聞き返しも除外します。

明示的な確定表現を抽出するときも、発言全体に曖昧語がないことを確認しています。「たぶん……、承りました」のように節をまたいでも、確定だけを取り出さないためです。

ただし、これは定義済みの表現に対する判定です。未知の言い回しを含め、すべての曖昧さを認識できるという意味ではありません。

## 3. 「はい」は、直前に何を聞いたかと組み合わせる

「かしこまりました」は、依頼を聞いたという返事にも、予約確定の返事にも使われます。

そのため `confirmed` は、主に次の経路で作ります。

- 店側が「ご予約承りました」など、確定表現を言った。
- 発信側が明示的に確定を尋ね、その直後に店側が肯定で答えた。
- 同じ確定質問への応答として、店側が日時・人数・価格などを言い直しつつ、予約する意思を述べた。

最後の経路は、`COMMIT_RE` と条件の再提示を組み合わせた処理です。以前の記事では確定経路を二つと説明していましたが、現行のコードにはこの分岐もあります。

肯定応答の判定では、疑問文や曖昧語、拒否を除外します。ただし、経路ごとの条件は完全に同一ではありません。[`ingest` の確定質問を処理する箇所](https://github.com/FORIFOR/oathra/blob/main/packages/evidence/src/engine.ts)で確認できます。正規表現の数だけで判定全体を説明できない理由でもあります。

## 4. 確定は、そのときの条件に紐づける

一度 `confirmed = true` になったら終わり、とはしません。

`engine.values()` は、確定が発言された時点の確認済み条件と、その発言内で再提示された条件からスナップショットを組み立てます。現在の値と異なる項目があれば、確定を返しません。

```ts
// packages/evidence/src/engine.ts より抜粋
const stale = Object.entries(snapshot).some(
  ([field, v]) => v !== undefined && out[field] !== v
);
if (!stale) out.confirmed = true;
```

たとえば1万8000円で確定した後に2万3500円へ訂正されたら、前の確定は失効します。新しい価格への合意と、その条件での確定が必要です。

このとき、必ず「予算違反」と表示されるわけではありません。未合意の新価格はまだ確認済みの値ではないので、まず `incomplete` になる場合があります。**条件を超えた提案が来たことと、その条件を受け入れてしまったことを区別する**ためです。

## 5. 取り消しは、条件変更とは別に扱う

価格も日時も変わらずに、「やはりご予約をお取りできませんでした」と言われることもあります。値の比較だけでは、この取り消しを検知できません。

そのため、店側の取り消し表現を受けた時刻を `retractedAt` に残し、それより前の確定を有効な値として返さないようにしています。同じ発言の中で確定の後に取り消しが続く場合も、抽出時に後続の文を確認します。

履歴は残りますが、現在の `confirmed` には使いません。画面が完了から未完了に戻るのは、この再評価によるものです。

## 検証で確認できたことと、まだ言えないこと

[既存の検証記録](https://github.com/FORIFOR/oathra/blob/main/docs/launch/miscompletion-cases.md)では、店員役の発言をエンジンへ直接入力して、次の結果を確認しています。

| 条件 | 結果 |
| --- | --- |
| 曖昧な返事 | 未完了、`confirmed` なし |
| 満席を断って19時半を提案 | 未完了、19時半は受諾待ち |
| 代案を受け、必要条件をそろえて店側が確定 | 完了、`time = 19:30` |
| 「承りました。ただ、料金は2万3500円になります」 | 未完了 |
| 1万8000円での確定後に2万3500円へ訂正 | 未完了、以前の確定が失効 |

これは文字列入力によるエンジンの確認です。入力例だけを抜き出した表なので、同じ順序・事前状態でなければ結果は変わります。

CIでは、用意した発言変異を使う1万runの敵対的シミュレーションも実施しています。誤完了0という結果は、その変異の範囲での観測です。実電話での誤完了率や、日本語全般への保証には置き換えられません。

また、厳しく判定するほど、本当は成立している予約を未完了として残す可能性があります。今後は誤完了だけでなく、取りこぼしも測る必要があります。音声認識の誤り、話者の取り違え、表現の網羅性も残る課題です。

## 自分の文字起こしを渡す

v0.1.12では、判定機能を`oathra/evidence`として読み込めるSDKと、ローカルの`oathra verify`コマンド、仮押さえ・未確定を完了扱いしないガード、シーン分岐付きの同意付き追加聞き取りを配布しています。明確な同意がない場合は任意聞き取りを繰り返しません。YAMLの `mission.intake` はローカルのシミュレーターから実電話へ引き継げます。既存の電話会社やモデルを切り替えず、手元の発言を入力できます。[導入手順](https://github.com/FORIFOR/oathra/blob/main/docs/INTEGRATION.ja.md)に入力形式と、保存済みの実モデル交渉記録を再評価する手順をまとめました。追加聞き取りの実演は[48秒のArena録画](https://forifor.github.io/oathra/#intake-video)で確認できます。

追加聞き取りを使う場合も、目的・同意・質問上限を契約に明示します。ランタイムは必要な通話条件の完了後に同意を尋ね、同意された質問への次の発話だけを `intake.json` と `summary.md` に保存します。同意と回答には発話ID・時刻が付き、未宣言の項目や推測した属性は記録しません。

[ブラウザで自分のログを検証するページ](https://forifor.github.io/oathra/check.html)も追加しました。インストールせずに、次の3操作で試せます。

1. 「公開済みの交渉記録を読み込む」を押すか、自分の文字起こしJSONを貼り付ける。
2. 「このログを検証」を押し、必須項目と完了状態を見る。
3. 「発言ごとの証拠履歴」で、値の根拠となった話者・発言・時刻を確認する。

入力はタブ内で処理し、送信・自動保存しません。[25秒の実操作動画](https://forifor.github.io/oathra/#transcript-video)では、公開済みのGPT-4o-miniとホテルシミュレーターの交渉記録を使用しています。実電話の記録ではありません。

この版では、英語の`7:30`を`07:30`として確定する不具合も修正しています。午前・午後が明示されなければ時刻を未確認にし、相手が予約確定を述べても完了条件を満たさないようにしています。以前の`7 pm`から午前・午後を推測する実装ではありません。
