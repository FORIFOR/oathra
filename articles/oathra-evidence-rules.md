前回の記事（[AIが電話で予約を取るOSSを作った](https://zenn.dev/forifori/articles/oathra-launch)）で「予約できたかどうかは店側の発言で判定する」と書きました。今回はその判定部分だけを切り出して書きます。コードは [packages/evidence](https://github.com/FORIFOR/oathra/tree/main/packages/evidence) にあります。LLM は一切使っていません。

## 何を防ぎたいか

電話の相手（店員）が言いそうな、判定が滑りやすい言い回しはだいたいこの 3 種類でした。

1. 「たぶん大丈夫ですが、まだ確定ではありません」 …… 曖昧な返事
2. 「19時は満席です。19時半なら空いています」 …… 断りと代案が 1 文に同居
3. 「承りました。ただ、料金は2万3500円になります」 …… 受諾のあとに条件変更

LLM に「予約は成立しましたか？」と聞くと、1 と 3 を「成立」と答えることがありました。会話の流れが自然だからです。そこで、成立の判定を LLM から外し、次の 4 つのルールに落としました。

## ルール 1: 発話を節に割ってから見る

「19時はいっぱいですが19時半なら空いております」を 1 文として扱うと、19:00 と 19:30 の両方が候補になります。逆接（ですが・ますが・けど・but）の直後で節を割り、前の節に否定語（満席・いっぱい・できません……）があればその節の値は「提案」にしません。

```ts
const sub = c.text.split(/(?<=ですが|ますが|けど|けれど|but\s)/);
```

これで 19:00 は候補から落ち、19:30 は「店側の提案」として残ります。提案は AI 側が「では19時半で」と受けるまで未確定です。

## ルール 2: 曖昧語が 1 つでもあれば、その発話は何も確定させない

```ts
export const HEDGE_RE =
  /と思います|と思う|たぶん|多分|おそらく|恐らく|かもしれません|かもしれない|確認してみ|確認いたします|確認します|調べてみ|probably|maybe|perhaps|I think|let me check|not sure|I'll check|might be/i;
```

「たぶん大丈夫です」は `大丈夫です` が同意語にも当たりますが、同意判定は `AGREEMENT_RE && !REFUSAL_RE && !HEDGE_RE` なので同意になりません。確定の判定も同じで、「たぶん……承りました」のように発話のどこかに曖昧語があれば `confirmed` は立ちません。

判定側だけでなく、かける側もこれに合わせました。以前のスクリプト脳は曖昧な返事に対して同じ依頼を繰り返して諦めていたので、いまは「念のため確認させてください。9月12日、19時以降、2名でご予約は確定とさせていただけますでしょうか？」と 2 回まで聞き返します（v0.1.1）。

## ルール 3: 「確定」は店側の明示的な言葉か、確定質問への「はい」だけ

`confirmed` が立つ経路は 2 つしかありません。

- 店側が「ご予約承りました」「お取りしました」などの確定表現を言った（`CONFIRMATION_RE`）
- AI が「……でご予約を確定してもよろしいでしょうか？」と質問し、店側が「はい」「かしこまりました」で始まる返事をした（`CONFIRM_REQUEST_RE` → `AFFIRMATIVE_RE`）

後者は、返事に疑問符や「いかがでしょうか」が含まれていれば不成立にします。「禁煙のお部屋でしたらご用意できます。1泊19,900円でございます。」は質問への答えではなく再提示なので、確定にしません。

AI 側の「予約できました」という発話は、どれだけ自信ありげでも証拠になりません。話者が `callee` のノードしか見ないからです。

## ルール 4: 確定は、そのとき成立していた条件に紐づく

「承りました」の後に「料金は2万3500円になります」と来たら、前の確定は失効します。実装は単純で、確定ノードが立った時点で確定していた値と、その発話内で言い直された値をスナップショットに取り、最終状態と 1 つでも違えば `confirmed` を出しません。

```ts
const stale = Object.entries(snapshot).some(([field, v]) => v !== undefined && out[field] !== v);
if (!stale) out.confirmed = true;
```

失効したら AI は取り直しの確認をします。「承りました。ただ、料金は……」のように同じ発話に逆接が入っている場合は、そもそもルール 1 で受諾扱いにならず、価格は提案として待ちになります。

## 実際に流してみた結果

店員役の発話をエンジンに直接流して確認した結果です（[検証記録](https://github.com/FORIFOR/oathra/blob/main/docs/launch/miscompletion-cases.md)）。

| 店員役の発言 | 結果 |
|--|--|
| 「たぶん大丈夫ですが、まだ確定ではありません」 | 未完了。confirmed なし |
| 「19時は満席です。19時半なら空いています」 | 未完了。19:00 は採用されず、19:30 は受諾待ち |
| 上に続けて「では19時半で」→「19時半に2名様でご予約承りました」 | 完了。time=19:30 |
| 「承りました。ただ、料金は2万3500円になります」 | 未完了 |
| 「1万8000円でご予約承りました」→「失礼しました、2万3500円です」 | 未完了。confirmed が失効 |

ブラウザでも試せます。`npx oathra demo` で「自分が電話に出る」を選ぶと、入力欄の下に上の言い回しがボタンで並んでいます。

## 正規表現でやることの限界

正直に書くと、この方式は言い回しの網羅性に依存します。1 万回の敵対的シミュレーション（店員役の発話を変異させる）で誤完了 0 を CI の条件にしていますが、それは「用意した変異の範囲で 0」という意味で、実通話の指標ではありません。

判定が抜ける言い回しを見つけたら [Issue](https://github.com/FORIFOR/oathra/issues) で教えてください。正規表現に 1 行足すだけで直ることが多く、それが一番助かります。
