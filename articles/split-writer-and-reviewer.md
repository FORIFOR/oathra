## 何が困るか

LLM に文書を書かせると、それらしい成果物がすぐ出てきます。困るのは、**出てきたものが正しいかどうかを、同じモデルに聞いても意味が薄い**ことです。
自分が書いた文章を自分で採点させると、だいたい通ります。結果、確認を省くか、全部人間が読み直すかの二択になります。

やったのは単純なことで、**書く役と確かめる役を別のエージェントに分け、確かめる役に「差し戻す」権限を持たせた**だけです。

このツール自体は[前回の記事](https://zenn.dev/forifori/articles/agent-team-launch)で紹介しました。そのときは Claude Code を繋いで動かし、
レビューが3件直っても最終状態が `partial` になった、という話でした。今回はその続きで、**外部APIを一切使わずローカルの Ollama だけで回したとき、
差し戻しが本当に起きるのか**を測っています。UIも作り直したので、そちらも載せます。

## 実装で効いた点

### 1. 確認の結果を2値にしない

いちばん効いたのはこれでした。pass / fail の2値にすると、**確認していないもの**が pass 側に落ちます。
実装では受け入れ基準ごとの結果を4値にしています（`backend/agentteam/contracts.py`）。

```python
status: Literal["pass", "fail", "unverified", "blocked"]
```

`pass` 以外が1つでも残れば、そのタスクは `accepted` ではなく `partial` になり、
`review left criteria unverified: <基準名>` が理由として残ります（`runtime/scheduler.py`）。
UI 側でも `unverified` は「確認は通過」と書かず、未確認のまま表示します。

### 2. 差し戻しは版を増やす。上書きしない

差し戻しのたびに成果物の版が増えます（`r1` → `r2` → `r3`）。上書きにすると、
「何を指摘されて、どこが直ったか」が消えます。版が残っていれば diff が読めるので、確認役が仕事をしたことを後から検証できます。

### 3. 「確認役が通した」と「依頼が完了した」を混ぜない

1ファイルが確認を通っても、依頼全体はまだ途中ということがあります。UI でこの2つを同じバッジで表すと、
利用者は完了していないものを完了と読みます。別々に出すようにしました。

## うまくいっていないこと

正直に書いておきます。

- **英語で動かしたとき、成果物の本文が日本語になることがある。** UI は英語に切り替わりますが、生成物のプロンプト側が追随しきれていません。既知の未修正です。
- **計画側が組んだ依存関係を自分で拒否することがある。** 上の収録中、計画の生成が3回連続で「reviewer のタスクが t1 に依存している」と自分の出力を却下し、先に進めませんでした。
  最終的には計画を挟まない経路（書く役＋確かめる役のみ）に切り替えて通しています。計画役の安定性は、この規模のモデルでは十分ではありません。
- **13〜15分かかります。** 手元のマシンとモデル次第で、速いとは言えません。
